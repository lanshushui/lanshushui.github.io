PlatformView 的原理

# Engine 创建流程

java 层调用 createAndRunEngine → attachToNative

1.c++ 层调用 AttachJNI 代码

2. 调用 AndroidShellHolder 的构造函数 代码 先后创建 ThreadHost ，利用 ThreadHost 提供的 taskRunner 创建 task_runners ， Shell 代码

AndroidShellHolder 通过唯一成员 std::unique_ptr<Shell> shell_ 管理整个 Shell 生命周期

3. 构造函数先创建 ThreadHost

  1. ThreadHost 构造函数调用 CreateThread 创建 4 个线程 代码
  2. CreateThread 创建 std::make_unique<fml::Thread> 代码
  3. fml::Thread 构造函数创建 std::make_unique<ThreadHandle> ，ThreadHandle 构造函数创建真正的线程 代码

再利用 ThreadHost 提供的 taskRunner 创建 task_runners ， 调用 Shell::Create 创建 std::unique_ptr<Shell>，传入 on_create_platform_view lambda 函数 等待创建 PlatformViewAndroid 代码

4.Shell::Create 调用 Shell::CreateWithSnapshot 方法创建 Shell 代码

# Engine spawn 流程

Shell::Spawn 不会为 UI / GPU / IO 三个 TaskRunner 再创建新的 fml::Thread，而是直接把 父 Shell 已经跑起来的那三条线程 拿来复用

1. 利用主 engine 的 flutterJNI 创建出新的 FlutterJNI，然后调用 engine 的构造方法

2. 用 native 方法构造出新的 FlutterJNI

3.native 层创建 java 层对象 FlutterJNI 代码来源

主 engine 的 nativeShellHolderId 属性是 engine 调用 attachToJni 方法赋值的，

spawn 的 engine 的 nativeShellHolderId 属性 是 c++ 层赋值的，因为此时的 flutterJNI 已经 attach 了

4.AndroidShellHolder::Spawn 这里把原本的 thread_host_传递进新 AndroidShellHolder 的构造函数中，复用了 thread_host_，创建新的 std::unique_ptr<AndroidShellHolder> 代码

5.Shell::Spawn 把原本的 task_runners_传递进 CreateWithSnapshot 方法中复用 代码

6.Shell::CreateWithSnapshot 代码

7.Shell::CreateShellOnPlatformThread 创建 std::unique_ptr<Shell> 代码

注意：我发现 c++ 层的 engine 也有 Spawn 方法，但是并没有找到调用链接，我们 java 层 spawn 一个 engine 时也是把 CreateEngine 方法 传入 CreateWithSnapshot 的参数中，最终调用 std::make_unique<Engine> 方法 代码

# Engine 摧毁流程

java 层调用 destroy→ detachFromNativeAndReleaseResources→ nativeDestroy

1.c++ 层调用 DestroyJNI 代码

2. 调用 AndroidShellHolder 的析构函数 代码

3. 调用 shell_的析构函数 主要是向各个 TaskRunner 抛任务 代码

4.ThreadHost 的析构函数没有额外代码，但它持有所有线程都是 unique 的，所以当 ThreadHost 析构时，所有线程都会析构停止，会调用 pthread_join 等待所有线程停止。 代码
